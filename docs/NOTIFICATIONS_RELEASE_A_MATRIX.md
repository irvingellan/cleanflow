## Publication and recovery invariants

- Fence the live Hosting version, Rules release and every Function revision against the reviewed baseline before mutations. A matching project name or inventory of Function names alone cannot detect a concurrent deploy. Compare an expected post-state at each boundary and stop when reconciliation is required.
- Publish session-compatible Rules before any writer can create an array membership. Update the session readers and manager FCM selectors before making their new writer behavior available. Keep legacy manager FCM registration requests and persisted legacy records valid during overlap. Publish Hosting only after the expected server state. Old Hub tabs can keep the scalar client check until they load the new build.
- Preserve the existing rules and session-aware server after rollback. The published prior Hub browser checks strict scalar equality. Adding a device retains the active scalar anchor so the old tab for that original installation stays signed in. The prior browser still rejects any additional installation. The compatible rollback artifact retains the session-aware client, disables the Inbox UI and reads, and resolves old cleaner Inbox links to the agenda. Exact prior Hosting restore requires evidence that no additional-device session has been issued.
- Avoid reverting the versioned manager registration implementation after it has written token/installation claims. If Inbox UI is rolled back, existing reads, receipts, device claims and pending trigger work must be preserved. Hosting rollback does not remove server endpoints; an emergency that requires disabling a server path needs a compatible server change.
- Future #86 enablement must re-review the deferred Assignment callable and Assignment trigger with the batch callable, Rules and visual controls. A retains the current manual path. B concerns cleaner push only.
